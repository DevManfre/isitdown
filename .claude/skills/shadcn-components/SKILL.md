# shadcn/ui Components

The dashboard's primitives (`Button`, `Card`, `Dialog`, the `chart.tsx`
`ChartContainer` wrapper, …) live under `src/ui/web/components/ui/` and are
generated by the `shadcn` CLI (`components.json` at the repo root configures
it: `style: "new-york"`, `baseColor: "neutral"`, CSS entry point
`src/ui/web/css/base.css`, aliases rooted at `@/`). `writing-code` says reuse
one of these before hand-rolling a component-level CSS class — this skill is
how to add or regenerate one without breaking the build or the theme.

Four hazards below were each hit for real during the port. Read all four
before running the CLI, not just the one that seems relevant.

## Hazard 1 — the CLI can't see the `@/` alias and writes into a stray `./@/`

The alias lives in `tsconfig.web.json` (`baseUrl: "."`, `paths: {"@/*":
["src/ui/web/*"]}`) because the root `tsconfig.json` excludes
`src/ui/web/**` entirely. The `shadcn` CLI resolves `@/` via
`tsconfig-paths`' `loadConfig()`, which only ever reads the **root**
`tsconfig.json` — it has no idea `tsconfig.web.json` exists. With no `paths`
in the root config, the CLI can't resolve `@/components/ui/button`, and
instead of failing loudly it writes the file to a literal `./@/components/ui/`
directory at the repo root.

Fix, every time you invoke the CLI:

1. Temporarily add to root `tsconfig.json`'s `compilerOptions`:
   ```json
   "baseUrl": ".",
   "paths": { "@/*": ["src/ui/web/*"] }
   ```
2. Run the `npx shadcn add …` call(s).
3. Revert immediately: `git checkout -- tsconfig.json`.
4. Confirm `git status` shows no diff on `tsconfig.json` and nothing under a
   stray `./@/` directory before committing.

Don't leave the patched `paths` in root `tsconfig.json` "since it's
harmless" — the root config's `exclude` still keeps `src/ui/web/**` out of
the server build; the `paths` entry is a CLI-only workaround, not a real
project setting.

## Hazard 2 — never run `npx shadcn add index`

`add index` (or any command that touches the CLI's base-styles step) rewrites
whatever file `components.json`'s `tailwind.css` key points at —
`src/ui/web/css/base.css` in this repo — with shadcn's own stock oklch
grayscale palette, a `.dark`-class dark-mode block, and its own
`@custom-variant dark (&:is(.dark *))`. That silently clobbers this repo's
theme: `base.css` currently just imports `tokens.css` and `motion.css` and
sets `body`'s background/color/font from CSS variables —

```css
@import "tailwindcss";
@import "./tokens.css";
@import "./motion.css";

body {
  background: var(--color-bg);
  color: var(--color-text);
  font-family: var(--font-body);
}
```

— and `tokens.css` is what actually defines the Nocturne palette across three
theme blocks (`:root`, `:root[data-theme="dark"]`,
`@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) {} }`)
plus the real `@custom-variant dark (&:where([data-theme="dark"],
[data-theme="dark"] *));` that binds Tailwind's `dark:` prefix to this
project's theme attribute (see Hazard 4). A CLI-rewritten `base.css` breaks
all of that, and the breakage doesn't announce itself — the page still
renders, just with the wrong palette and a dead `dark:` prefix.

This was run once during the port (to recover a missing `lib/utils.ts`) and
the damage was only caught by reading `git diff` afterward, then fixed with
`git checkout -- src/ui/web/css/base.css` plus `npm uninstall tw-animate-css
shadcn` (see Hazard 3).

**Rule: after every `npx shadcn` invocation, run `git diff` before staging
anything.** Don't assume a component-scoped `add` only touched the component
file — check `base.css`, `package.json`, and `package-lock.json` too.

## Hazard 3 — the CLI drifts dependencies

The CLI installs whatever a component needs, and it isn't picky about where:
it has put packages straight into `dependencies` (this is a server repo — the
web bundle is built at image build time, so a browser-only package doesn't
belong in the runtime image's dependency tree at all) and it has pulled in
packages this repo doesn't want (`tw-animate-css`, and `shadcn` itself as a
devDependency, both added as a side effect of one `add index` call).

Production `dependencies` in `package.json` must stay exactly:

```
express, yaml, zod
```

Everything the dashboard needs at build time — `react`, `react-dom`,
`react-router`, `react-i18next`, `i18next`, `@tanstack/react-query`,
`recharts`, `radix-ui`, `class-variance-authority`, `clsx`, `tailwind-merge`,
`lucide-react`, and the shadcn CLI's own runtime helpers — belongs in
`devDependencies`, because Vite bundles it into static assets during
`npm run build`; none of it needs to exist in the runtime `node_modules` the
`light`/`ui` Docker stages install with `--omit=dev`.

After any `add`, diff `package.json`: move anything that landed in
`dependencies` but isn't `express`/`yaml`/`zod` into `devDependencies` (or
uninstall it if the port doesn't actually use it), and remove any package the
task at hand didn't ask for.

## Hazard 4 — dark mode is `[data-theme="dark"]`, not shadcn's `.dark` class

`index.html` has a pre-paint script that stamps `data-theme="light"` or
`data-theme="dark"` on the root element before first paint (avoiding a flash
of the wrong theme); "system" deliberately stamps nothing and falls through
to the `prefers-color-scheme` media block in `tokens.css`. `tokens.css`
declares:

```css
@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));
```

which rebinds Tailwind's `dark:` utility prefix to that attribute. A
generated component using `dark:bg-...` works correctly because of this
override — but if a fresh `add` ever reintroduces shadcn's own
`@custom-variant dark (&:is(.dark *))` (see Hazard 2), every `dark:` class in
every component silently stops firing, because nothing in this app ever adds
a `.dark` class to anything. If dark mode looks wrong after touching
`components/ui/` or `base.css`, check this line first.

Two related conventions generated components must fit into, not fight:

- **`motion.css`** selects entry-animation states on `data-slot` and
  `data-variant` attributes (e.g.
  `[data-slot="button"][data-variant="default"]:hover`), which shadcn's
  "new-york" style components already emit — don't add a second animation
  or transition system on top of what a generated component already has.
- **`cn()`** from `@/lib/utils.ts` (`clsx` + `tailwind-merge`) is the one way
  to compose conditional class names — every generated component already
  uses it; don't hand-roll template-string class concatenation in a new one.

## Generated components and `exactOptionalPropertyTypes`

Both `tsconfig.json` and `tsconfig.web.json` set `exactOptionalPropertyTypes:
true`. shadcn's generated component source doesn't always satisfy that (an
optional prop typed as `T | undefined` explicitly assigned `undefined`, where
this setting wants the property simply omitted). When `npm run typecheck`
flags a freshly-generated file:

- Fix it in place — this is a real type error, not a false positive.
- **Say what you changed and why**, in the commit or PR description that
  introduces the component. A later `npx shadcn add <same component>` will
  overwrite the file from scratch and silently reintroduce the same error —
  the fix does not "stick" across a regeneration, so the next person (or you,
  months later) needs to know it has to be reapplied.

## Charts specifically

Chart primitives (`src/ui/web/components/ui/chart.tsx`, the `ChartContainer`
wrapper) come from the CLI the same way; the port's own chart components
(`UptimeRing`, `UptimeStrip`, `UptimeBarRow` under
`src/ui/web/components/charts/`) layer a repo-specific convention on top —
see `ui-dashboard-charts` for the data-flow rules. The component-level
pattern to follow:

```tsx
import { ChartContainer } from "@/components/ui/chart.tsx";
import { chartConfigFor, statusFill } from "@/lib/chartConfig.ts";

<ChartContainer config={chartConfigFor()} className="anim-ring size-20">
  <RadialBarChart data={[{ name: provider.id, value }]}>
    <RadialBar dataKey="value" isAnimationActive={false} fill={statusFill(status)} />
  </RadialBarChart>
</ChartContainer>
```

- `chartConfigFor(scale)` (in `src/ui/web/lib/chartConfig.ts`) is the single
  place status-to-colour mapping is declared, reading `var(--status-*)`
  tokens from `tokens.css` by name — never inline a hex or oklch value in a
  chart component.
- `isAnimationActive={false}` on the Recharts primitive is deliberate: entry
  motion is handled once, by the `anim-*` classes and the `key`-forced
  remount in `App.tsx`, not by Recharts' own transition system. Don't turn
  Recharts animation back on "to make it smoother" — it fights the app's
  single animation mechanism.

## Checklist before committing anything touched by the CLI

- [ ] `git diff tsconfig.json` is empty (Hazard 1 workaround was reverted).
- [ ] `git diff src/ui/web/css/base.css` shows only changes you intended —
      if you ran `add index` or anything base-styles-related, it should show
      **no** diff at all.
- [ ] `git diff package.json package-lock.json` — `dependencies` still reads
      exactly `express`, `yaml`, `zod`; nothing unrequested was added.
- [ ] `npm run typecheck` passes; any fix required by
      `exactOptionalPropertyTypes` is called out in the commit/PR body.
- [ ] Dark mode still renders correctly (toggle it, or check
      `tokens.css`'s `@custom-variant dark` line is unchanged) — see Hazard 4.
